# Architecture

```text
                  AWS us-east-2: default VPC, Elastic IP
                  +-- Ubuntu arm64 t4g.small / Docker Compose --------+
Phone --HTTPS---->| Caddy --HTTP--> census --JDBC--> Postgres           |
                  | TLS, no access  policy, health,  encrypted gp3     |
                  | log             Flyway schema   daily pg_dump    |
                  +--------------------------------------------------+
                        ^                 |                 |
GitHub OIDC / operator --SSM (no SSH)     host metrics      S3 backups
                        ^                 |                 14-day lifecycle
                   SSM parameters     CloudWatch --> SNS email

AWS wrapper: account budgets + automatic EC2 stop; daily cost anomalies;
             multi-region CloudTrail management events --> S3 (14 days)
```

Census validates environment configuration (including the required hash pepper), migrates through V11 and checks the pepper against the database's, replays withdrawals, applies the monotonic filter floor, and drains startup lifecycle work before accepting HTTP. The five-connection Hikari pool is registered with Exposed. Migration, recovery or lifecycle failure aborts startup. Readiness runs a bounded `SELECT 1`; liveness does not check the database. Signed, budgeted ingestion and authenticated operator review share the same effective policy.

## Contract seam

`../DashBuddy/census-contract` is an Apache-2.0 Gradle included build with coordinates `cloud.trotter.census:contract:0.0.0-local` and package `cloud.trotter.census.contract`. `censusContractPath` overrides its location. A reference to `CensusHash` proves dependency substitution at compile time. DTOs, fingerprinting, hashing, and grammars stay in that build; no crypto dependency or duplicate wire implementation is introduced here. The included contract owns hash-domain, DTO and fingerprint constants; both workflows retain pin `cb175f9ec58f7186ea6efe811766a3042be45550`.

## Storage and deployment boundary

V5 adds three attributable replacement tables and one policy-only floor table, retaining empty legacy tables. Tokens and vocabulary partition by `(hash_domain, filter_rev, token_hash)`; token evidence additionally keys by install. Cluster sightings carry exact domain/revision and observation day. Sample caps remain five per fingerprint/app-version and one per receipt day across revisions. Validated observation days, clamped to receipt day for the one-day future tolerance, govern evidence age; retries and backfills do not refresh it. V1–V4 and their checksums are unchanged.

V7 (#85) is a Flyway Java migration, the one migration that is not SQL, because it needs the pepper and the pepper never enters SQL or the database. It rewrites every stored word hash (`token_hash` in the token and vocabulary tables, every slot `h` in `cluster_samples`) to `HMAC-SHA256(pepper, label + hash)` cut to the census width, re-keys notification fingerprints (full width) in `clusters`, in every column a foreign key points from (found from the catalog) and inside the stored notification samples, keys every client batch id in `ingest_ledger.batch_ids` (the app derives them from the batch's public fingerprints or envelope bytes), and records the pepper's HMAC check value in `hash_keying`. Flyway runs it in one transaction with its history row: an interruption rolls it all back and the next start reruns it, and once committed it never runs again. `Database.flyway` is the one migration set; a Flyway built without V7 stops at V6. Ingest applies the same keying before any write (`HashKeying.atRest`), so a migrated row equals what ingest stores for the same item. Screen fingerprints cover class and id only and stay public. Equality is preserved, so every join, k count and cross-version comparison is unchanged. A notification's stored key is `HMAC(pepper, public fingerprint)` (`storedKey`), one identity that needs no sample: ingest computes it from the item it validated, and V7 from the stored key alone, so a resolved cluster whose samples have expired keeps its status, versions and sightings when the same notification arrives again. A keyed body can no longer prove its fingerprint, so V7 first runs the V5 legacy cutover (`LegacySampleCutover`) on null-provenance samples while they are still public: a valid one is scrubbed, given its provenance and stored under its coming key; an invalid, resolved or expired one is deleted, and captures paired with those clusters go. The startup bootstrap runs the same cutover afterwards and finds nothing; a null-provenance sample with keyed slots cannot prove its key and is deleted.

V8 (#86) is the second Java migration: epoch pseudonyms at rest (ADR-0011 §21). The content tables stop naming the install. Token sightings, cluster sightings and per-install health are keyed by an epoch tag, `HMAC-SHA256(epoch key, purpose ‖ install id ‖ object)`, beside an `epoch` column, and their `install_id` columns are dropped. An epoch is 30 whole UTC days on a fixed grid from 1970-01-01 (epoch `n` covers days `[30n, 30n + 29]`, `Epochs`). The object is the keyed token with its domain and revision for a token sighting, the stored cluster key for a cluster sighting, and nothing for health (the alarms read one install's own history within the epoch). One phone therefore has one tag per object within an epoch and unrelated tags in the next, and its tags for two tokens are unrelated even within an epoch. A row is tagged under the epoch of the day it describes (observation or report day), so a late report for yesterday lands on yesterday's row after a boundary. Only `installs`, `nonces` and `ingest_ledger` (authentication, quotas) and `trusted_envelopes` (the operator's own devices) keep an install id, and since V10 `contributor_grants` (#81); `PublicInstallsTest` and the startup shape check (`db/lifecycle-shape.sql`) refuse any other.

Each epoch has its own random 32-byte key in `epoch_keys`, wrapped with AES-GCM under a key derived from the pepper (the epoch number is authenticated data). It is created on first use, or ahead of need by the lifecycle sweep, for the previous, current or next epoch only. The sweep deletes every key older than the previous epoch (`EpochKeyStore`). Because a key is random, not derived from the pepper, deleting it destroys it: its rows can no longer be tied to any install, the operator included, once the last backup holding the wrapped key has expired (see [Operator](OPERATOR.md#epoch-keys)). Retention removes those rows anyway, since every content table keeps at most 30 days and a key outlives its epoch by a full epoch.

Withdrawal, "delete my data" and revocation recompute the install's tags under every stored key (an expired key the sweep has not yet deleted included, since its rows are still linkable), one per object stored in that epoch, and delete the matching rows; the restore replay does the same, so rows under a destroyed key are skipped, never a failure. Vocabulary promotion share-locks the token's sighting rows and counts only that locked cohort, so a sighting stored after the lock never adds to it, and a withdrawal or trust change of a counted install waits for the promotion. k counting can no longer join `installs`, so ingest stamps each sighting with the install's `trusted` flag and, during its first week, the day its evidence starts to count (`counts_from`, cleared by the sweep once passed); a trust change updates the stored rows under the install lock, and revocation deletes them. k is counted within one epoch: per (partition, token) or cluster, the distinct tags of each epoch, and the largest of those counts. V8 first checks the configured pepper against the one V7 recorded (a mismatch rolls it back unchanged), then tags existing rows the same way (a row already past retention under the previous epoch), deletes revoked installs' sightings, and drops the empty pre-V5 tables. Epoch keys are unwrapped per transaction and never cached or kept in a thread-local. One limit is outside the schema: PostgreSQL's system columns (`xmin`) mark rows written by one transaction, so they can correlate an install's rows within that transaction for anyone with live database or disk access; logical backups carry none ([Security](SECURITY.md#epoch-pseudonyms-at-rest-86)).

V9 (#80) adds `slot_sightings`, the per-slot evidence for slot constancy (ADR-0011 §14). Token sightings say which installs saw a word, not where it sat, so they cannot tell a slot's chrome from its values. A slot sighting is presence only, one row per (cluster, app version, domain, revision, raw layout, slot, epoch, value, epoch tag), plus a `present` row per slot; the value is the keyed hash or a marker. The layout id (`SlotWalk.layout`) hashes the raw tree's shape, wrappers included, so one slot path names one node across the rows counted together even though the fingerprint splices wrappers away. The tag's object is the whole row identity, value included (`TagPurpose.SLOT`, `SlotObject`), so one install's values carry unrelated tags as its tokens do. Each row keeps its own newest observation day (`last_day`, retention). Rows reference `clusters` with `ON DELETE CASCADE`, carry `trusted` and `counts_from` like token sightings, and are part of every erasure (`TaggedTable.SLOTS`); erasure and trust changes stream each epoch's objects with a bounded fetch size and match tags chunk by chunk (`TaggedTable.forEachTagChunk`), for every tagged table. The classifier (`SlotConstancy.classify` over `SlotEvidence.of`) is pure. The operator views read live counts (`slotReadings`); a contributor's phone reads the day's release instead (V10, below).

V10 (#81) adds the contributor tier (ADR-0011 §15). `contributor_grants` is the one new table that names an install (a
permission, like the quota ledger; the startup shape check allows it); `contributor_reads` is the audit log of
contributor reads, keyed by grant id and deleted with the grant. Contributor quotas are new counters on the install's
`ingest_ledger` row. `slot_confirmations` and `slot_roles` are tagged like slot sightings (`TagPurpose.CONFIRMATION`,
`ROLE`; the object is the slot identity with the confirmed keyed hash or the role in the value's place), carry
`trusted`, and keep 30 days. `slot_release` (with its day header `slot_release_days`) is the day's copy of the counted
slot rows as they stood at the end of the previous day, under their own slot tags: V10 adds `first_received`,
`received_day` and `prev_last_day` to `slot_sightings` (ingest keeps the last day a row had before its latest receipt
day; rows written before V10 take the migration day as their receipt), and `SlotRelease.buildRelease` copies the rows first received before today, each with that earlier last day when
it was written again today, in one `INSERT … SELECT` inside a transaction holding the table's EXCLUSIVE lock, and every erasure of the table takes ROW EXCLUSIVE first
(`TaggedTable.RELEASE`), so an erasure either precedes the copy or deletes the copied rows after it commits. Contributor
reads (`ContributorStore.classes`, the gate) run in one REPEATABLE READ snapshot, answer only a reader with a live
sighting of the variant (or slot), and leave the reader's rows out by recomputing its tags over the rows they read
(`SlotRelease.leaveOneOut`); the quota and audit row are written first, in their own transaction. Contributor request
bodies refuse a repeated JSON key (`hasDuplicateKeys`), and the quarantine seals the validated artifact's canonical
form. Writing transactions share-lock the install row before the grant. Erasure deletes quarantine items before
trusted envelopes (whose deletion locks clusters), the order approval takes (item, then cluster). `contributor_words` holds gated words, unlinked to any install, until the operator resolves them.
`quarantine_items` holds "Ask the developer" artifacts sealed to the operator's X25519 key (`QuarantineCrypto`; the
offline opener is `deploy/tools/QuarantineKey.java`), tagged by item id for erasure, and nothing outside the quarantine
routes reads it; `backup.sh` dumps it, `slot_release` and `slot_release_days` without rows. Withdrawal, data deletion,
revocation and the restore replay erase the new tagged tables through `TaggedTable`; withdrawal deletes the grants. The
lifecycle sweep builds the day's release, deletes an older one even when the build fails, and expires confirmations,
role tags, audit rows, expired grants, waiting words and quarantine items.

V11 (#82) adds the anchor check (ADR-0011 §16). `anchor_check_budget` counts candidates per caller and UTC day (7
days); `anchor_checks` is its audit log, one row per query (30 days). Neither names an install: a caller is a fixed
name (`operator`; the agent token, #84, adds its own, `AnchorCaller`). `AnchorCheckStore.check` runs in one
transaction: the pure chrome filter (`ChromeShape.anchorCandidate`) first, then the budget, then, only for a query
with no refused candidate, the slot's live counted rows (`SlotRelease.liveRows`, classified like the operator views
with nobody left out), the keyed compare of every case variant (`anchorMatches`) and the audit row. Every slot class
runs the same statements and the same hashing; only `constant` supplies a value to compare against.

Configuration is injected, stdout carries logs, and PostgreSQL holds durable state. The runtime is non-root, drops capabilities in Compose, and writes only under `/tmp`. Flyway coordination handles concurrent migration attempts, but operators must still review backward compatibility for rolling deployments.

## AWS wrapper — S2

[deploy/aws](../deploy/aws/README.md) wraps the same Compose stack in one Graviton EC2 instance, with IMDSv2, encrypted storage, restricted egress, and SSM-only administrative access. Parameter Store supplies startup secrets. Daily database dumps go to a private versioned S3 bucket; current and noncurrent versions have 14-day expiration rules. CloudWatch collects host memory/root-disk metrics and alarms alongside EC2 status/CPU metrics; no app logs are shipped. CloudTrail records management events separately from application traffic.

GitHub Actions assumes a ref-restricted OIDC role to deploy through SSM. Account-wide budgets notify and automatically stop the instance at the configured $50 threshold, subject to billing delay; this is not a guaranteed spending cap. Native S3 lockfiles protect Terraform state. The single root volume is a single point of failure, so instance replacement requires a backup/restore plan. No ECS, RDS, load balancer, or Kubernetes layer is introduced. Future ingress and logging changes must preserve the no-IP-retention promise.

## Notification storage and operator boundary — #1189 slice 2

Both workflows pin the included DashBuddy contract to reviewed commit `cb175f9ec58f7186ea6efe811766a3042be45550` (the v2 skeletons, #78). The server uses its DTOs, dispatcher, fingerprint and rejection vocabulary directly. Conformance reads the pinned JSONL corpus, notification vectors and manifest (counts and SHA-256), rather than fixed row counts. The synthetic metadata identity vector remains valid at the contract layer but is rejected by the unchanged server release-tag policy as `bad_version`.

V4 adds checked, non-null `clusters.kind`, backfilling existing rows to `screen`; V1–V3 are unchanged. Ingest persists the submitted contract kind without updating an existing cluster's kind and refuses conflicting kinds transactionally. Canonical samples, cluster sightings, token sightings and shared quota accounting commit in one transaction. Samples are capped at five per `(fingerprint, platform_app_version)`, with at most one per receipt day. V5 tokens used `(hash_domain, token_hash, filter_rev, install_id)`; since V8 (#86) the key is `(hash_domain, token_hash, filter_rev, epoch, install_tag)`, and equal chrome tokens still count an install once per epoch across screen and notification surfaces.

Operator samples are bounded allowlisted projections. Notification channels and notes use the live k=10 community-install gate in the existing 28-day ops counting window, or the existing trusted-sighting exception; falling below the gate hides them again. Slot hashes never leave sample projections, including above the gate. Historical samples with expired hashes can render kind badges without recomputing or changing cluster identity. Notifications never select a trusted screen capture or wireframe and cannot generate/store/download rule drafts. Classification uses the existing `screen_class` column and vocabulary. Health schemas, fleet denominators and alarm thresholds are unchanged.

## Shared lifecycle and configuration activation — #1189 slice 4

`CENSUS_NOTIFICATIONS_ENABLED` is strictly `true|false`, default `false`; `CENSUS_MIN_FILTER_REV` is a positive integer, default 1. The effective floor is the maximum of configuration, database policy and imported recovery journal. One policy is advertised by `/v1/policy` and returned at enrolment. Enrolment needs only one accepted schema among those the client lists (DashBuddy #1522); admission checks each item against the policy. Positive old revisions are rejected as server-owned `filter_rev_too_old`; malformed revisions remain `bad_item`. Claimed revision is not filter attestation or server reclassification.

Live vocabulary eligibility requires k=10 distinct unrevoked, non-trusted installs within one 30-day epoch (#86: distinct epoch tags per epoch, the largest epoch count, never a sum across epochs), seven full UTC days after the enrolment day (an install enrolled on day D counts from D+8, so one enrolled at 23:59 still waits seven complete days; no enrolment instant is stored, #79, and ingest stamps that day on the install's first-week sightings, #86), accepted provenance and unexpired per-install token evidence. Cohorts never pool domains or revisions; token first sightings never infer earlier enrolment. Every queue/count/display/resolve re-evaluates eligibility; operator resolution share-locks the token's sighting rows (which withdrawal, revocation and trust changes write under the install lock) and queries again. Hash-free dashboard projections, human review, trusted screen drafting at k=1 and notification capture/draft restrictions remain. Server deletion cannot retract a shipped bundle.

Token evidence expires at last observation +30 days and cluster evidence (presence rows, #79) at +30; unresolved samples at +90 days after the cluster's last observation. Resolution stamps once and caps sample lifetime at +30, including after reopening. Sample sweeps independently find orphan hashes, replacing every expired slot with `{"kind":"expired"}` without changing fingerprints. Reads also enforce deadlines; notes expire with samples. Inactive installs use parent-first erasure at 365 days. Envelopes expire at +30 with coordinated draft deletion; per-install health=30 (folded into `health_fleet_daily` before deletion, #79), ledger=7, backups=14 and withdrawal tombstones=60 days. All deadlines are half-open UTC (`deadline <= today`).

Startup catch-up drains capped work or fails closed; runtime passes run at UTC 00/06/12/18 with prompt continuation after caps and an independent seven-hour watchdog. Sweeps use bounded transactions, cancellation propagation and independent failure reports. Ingest and sample maintenance share cluster locks and recheck after locking. `/ops/lifecycle` and its dashboard summary contain activation, floors, aggregate counts/ages and bounded failure indicators only. Lifecycle failure/backlog/stale alarms use the existing sink and host publisher.

Cutover requires stopping the old server. Unknown-provenance legacy sightings and vocabulary are discarded, valid samples get embedded provenance and lose all legacy hashes, malformed samples are removed, and historical resolved samples expire immediately. Derived notes/drafts and inseparable captures are cleared; classification survives while the catalogue row is needed. V8 dropped the emptied legacy tables (#86); startup re-checks the lifecycle table shape and refuses a content table that names an install. This deliberately resets historical cohorts and requires fresh evidence to rebuild k.

Floor increases durably commit before removal and replay after interruption or older-backup restore. Restore requires current deployment policy plus the latest off-host floor and withdrawal journals. Floor journals are policy-only and retained while any older dump is restorable. Notifications remain disabled until integration tests, restore drill, zero overdue work and alarm delivery are verified; see [activation and rollback](OPERATOR.md#notification-activation-and-rollback).
